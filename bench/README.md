# Стенд вимірювань

Сценарії для розділу 4 записки: скільки трафіку вмісту дошки коштує робота в
кожній зі стратегій синхронізації. Ганяє справжній застосунок у безголовому
Chromium (Playwright), кожен прогін — зі свіжими акаунтами.

| Стратегія | Назва       | Що це                                                                                            |
| --------- | ----------- | ------------------------------------------------------------------------------------------------ |
| 1         | `per-event` | кожна подія жесту — окремий пакет усім на дошці                                                  |
| 2         | `batched`   | правки жесту — один пакет на кадр анімації, усім на дошці                                        |
| 3         | `aoi`       | як 2, але вміст поділений на клітинки 2000×2000, і клієнт отримує лише клітинки біля свого вікна |

Режим кімнати вибирає **сервер** (`SYNC_STRATEGY` у `.env`, типово `aoi`) і
оголошує його клієнтам першим кадром у сокеті. Стенд перед кожним прогоном
переставляє його через `POST /api/bench/strategy` — ручка відкрита лише з
`BENCH_METRICS=1`. `?sync=` в адресі більше не діє: саме з того, що режим жив
у `localStorage` браузера, і розʼїхалась кімната (журнал 05.10). Після
відкриття дошки стенд звіряє, що клієнт узяв потрібний режим, по
`data-strategy` на `.sync-status` — не збіглось, прогін падає, а не міряє не те.

## Що потрібно

1. Застосунок запущений локально: база, сервер і клієнт — як у кореневому
   README (`npm run dev` у корені; клієнт на `http://localhost:5173`).
   Сервер — з `BENCH_METRICS=1`: без нього стенд не прочитає лічильники й не
   переставить режим кімнат.
2. Ліміт реєстрацій: якщо сервер запущений не з `NODE_ENV=test`, діє
   обмеження 10 реєстрацій за 15 хв з однієї адреси. `strategies` бере
   2 акаунти, `aoi` — 4: два прогони поспіль вкладаються, третій може
   впертись у ліміт (тоді зачекати 15 хв).

## Запуск

```sh
cd bench
npm install
npx playwright install chromium   # лише перший раз
npm run strategies                 # стратегії на одній ділянці: пакетування
npm run aoi                        # велика дошка, люди в різних місцях
npm run load                       # навантаження 5/10/25/50 учасників (довго)
npm run charts                     # графіки з results/load.json
```

Інша адреса застосунку — `BENCH_BASE=http://host:port`. Лише частина
стратегій — `BENCH_STRATEGIES=batched,aoi`.

Щоб перевірити режим руками в одному браузері, не чіпаючи сервер, клієнта
треба зібрати з `VITE_ALLOW_SYNC_OVERRIDE=1` — тоді `?sync=` знову діє. Але
сервер такого клієнта в кімнату з іншим режимом не пустить: закриє сокет кодом
4001, і в devtools буде видно причину.

Результати — у `results/*.json` (і в консолі таблицею). Створені дошки
стенд видаляє за собою; тестові акаунти лишаються в базі (видалення акаунта
в застосунку нема).

## Навантажувальний прогін (`npm run load`)

12 прогонів: 5 / 10 / 25 / 50 учасників × три стратегії. **Близько години**,
здебільшого без нагляду — але машину на цей час краще лишити у спокої: на
50 вкладках браузери займають більшу частину памʼяті й усі ядра, і стороннє
навантаження зіпсує саме ті числа, заради яких усе й ганяється.

Потрібен сервер із `BENCH_METRICS=1` (інакше стенд одразу впаде: без
`/api/metrics` рахувати ресурси нема з чого) і з `NODE_ENV=test` — 12 прогонів
беруть 135 акаунтів, ліміт реєстрацій інакше зупинить усе на першій же сотні:

```sh
NODE_ENV=test BENCH_METRICS=1 npm run dev -w server   # у корені
cd bench && npm run load && npm run charts
```

Результат дописується в `results/load.json` **після кожного прогону**, і
повторний запуск замінює лише ті рядки, які міряє зараз. Тож обірваний прогін
не втрачає зробленого, а доміряти окремі точки можна так:

```sh
BENCH_N=50 npm run load                  # лише 50 учасників
BENCH_N=25 BENCH_STRATEGIES=aoi npm run load
```

Інші ручки: `BENCH_ACTIVITY_MS` (скільки триває активність, типово 12000),
`BENCH_DRAIN_MS` (скільки щонайдовше чекати збіжності, типово 300000),
`BENCH_PARALLEL` (скільки вкладок заводити разом), `BENCH_DEBUG=1` (рядок на
кожного клієнта: жести, кадри, позиція — цим видно, чи всі працювали).

`npm run charts` робить із `results/load.json` чотири графіки (svg і png,
подвійна щільність) у `results/charts/`. `npm run clock-skew` — окреме
калібрування: наскільки розходяться годинники вкладок, бо саме на їхній
спільній шкалі міряється затримка.

Прогін вважається дійсним, лише якщо в ньому `idleClients: 0` (усі клієнти
справді тягали свої обʼєкти). Поле `converged` каже, чи стани зійшлись: якщо
`false`, трафік у цьому рядку — нижня межа, бо частину пакетів приймачі так і
не отримали.

## Що саме міряється

- **Кадри вмісту** — вебсокет-кадри типу `UPDATE` (0) і `CELL_UPDATE` (22):
  лічильник обгортає `WebSocket` у кожній вкладці ще до завантаження сторінки.
  Присутність (курсори, виділення), чат і голос не рахуються — вони однакові
  в усіх стратегіях.
- **Жест** — 30 подій руху, які сторінка шле сама рівно по N на кадр анімації
  (`requestAnimationFrame`). Так частоту введення задає сценарій, а не затримка
  керування браузером: 1 подія/кадр — миша 60 Гц, 3 — 180 Гц.
- **Кінцевий стан** — обʼєкт зі стору як JSON у того, хто тягне, і в сусіда;
  між стратегіями він має збігатись байт у байт.
- `aoi.mjs` — пʼять далеких ділянок (кожна в своїй клітинці сітки), четверо
  людей: двоє в ділянці A, по одному в B і C. Кожен тягне обʼєкт у своїй
  ділянці; рахуємо, скільки вмісту отримав кожен з інших. Далі B переходить
  панорамою в A (має наздогнати живий стан) і назад (має перестати отримувати
  правки з A), а в кінці — чи всі обʼєкти лишились у базі.

Обмеження, які варто памʼятати при читанні чисел: це один комп'ютер і
локальна мережа, тож затримок і втрат тут нема; Chromium на справжньому
залізі сам вирівнює події миші по кадрах, тому рядки «3 події/кадр» —
модель невирівняного введення, а не твердження про Chrome (журнал 27.09).
