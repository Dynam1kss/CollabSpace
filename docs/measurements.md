# Результати вимірювань

Короткий зріз чисел до розділу 4. Сирі дані, журнал кампанії та повні умови
прогону — в `bench/results/final-2026-10-14/`.

## Що міряли і чому

Головне питання роботи: скільки вмісту дошки доводиться приймати одному
учаснику, щоб зробити ту саму роботу, і як це залежить від кількості людей у
кімнаті. Порівнюються три стратегії синхронізації, перемикані на сервері:

- `per-event` — кожна подія жесту окремим пакетом усім на дошці;
- `batched` — правки жесту одним пакетом на кадр анімації, теж усім на дошці;
- `aoi` — як `batched`, але вміст поділений на клітинки 2000×2000, і клієнт
  отримує лише клітинки біля свого вікна.

Міра трафіку — кадри вмісту (`UPDATE` і `CELL_UPDATE`) на один власний жест
клієнта. Присутність, чат і голос не рахуються: вони однакові в усіх стратегіях.

## Стенд

- AMD Ryzen 7 7700X, 8 фізичних / 16 логічних ядер; 32 ГБ DDR5
- Windows 11 Pro 10.0.26200, Node v24.21.0, PostgreSQL 16.15
- безголовий Chromium 153 через Playwright 1.63
- генератор навантаження, сервер і база — на одній машині, мережа loopback
- жест: 30 подій руху по 3 на кадр анімації; активність 12000 мс на прогін
- кампанія 14.10.2026, 28 прогонів за 106 хвилин

p95 — медіана по повторах там, де повтори є (`aoi` на всіх чотирьох точках і
`batched` на 5 і 10 — по три прогони; решта — один прогін). Кадри на жест,

мінімум за весь прогін, тобто найгірший момент.

Зірочка — прогін, у якому стани не зійшлися за відведені 300 секунд: трафік
там є нижньою межею, бо частину пакетів приймачі так і не отримали. У
`per-event` на 50 клієнт устигає лише один жест, тому 201 кадр на жест не
можна порівнювати з 744 на 25 — рядок лишено для повноти.

## Застереження

Від 25 учасників машина завантажена повністю (16 із 16 ядер), а на 50 у
широкомовних стратегіях закінчується вільна памʼять: 87 і 89 МБ у найгіршому
моменті. Там вузьке місце — сам генератор і машина, а не протокол, тож
затримки й час збіжності на 25 і 50 треба читати як верхні оцінки. На 5 і 10
машина має запас, і числа описують саме стратегії. Мережа loopback, тож
затримок і втрат немає — виміряні затримки є нижньою межею для реальної мережі.

## Як повторити

Потрібен застосунок, запущений локально, і сервер із `BENCH_METRICS=1` та
`NODE_ENV=test` (без другого ліміт реєстрацій спинить прогін: 12 прогонів
беруть 135 акаунтів). Докладніше — `bench/README.md`.

```sh
NODE_ENV=test BENCH_METRICS=1 npm run dev -w server   # у корені
cd bench && npm run load && npm run charts
```

Повну кампанію з етапами й повторами, яка сама підіймає застосунок і складає
`aggregated.csv`, робить `node final-campaign.mjs` у теці `bench`. Графіки —
`bench/results/charts/`.

## Автоматичні перевірки

Сервер — 238 перевірок у 18 файлах, клієнт — 386 у 43, разом 624. Запуск:
`npm test -w server` і `npm test -w client` (серверні ходять у базу, тож
потрібен піднятий postgres).
